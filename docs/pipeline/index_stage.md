# Модуль `index_stage.py` (Техническая документация)

## 1. Назначение и Архитектурная роль
Модуль `index_stage.py` отвечает за генерацию фундаментальных структур данных поискового движка:
1. **Инвертированный индекс тегов на Roaring Bitmaps** (`step_build_bitmaps`): преобразует списки вхождений постов для каждого тега в сжатые бинарные структуры Roaring Bitmap, упакованные в шардированные архивы `.roarpack` с индексными файлами прямого доступа.
2. **Колоночные Memory-Mapped массивы метаданных** (`step_build_mmaps`): переводит ключевые атрибуты постов из Parquet в плоские непрерывные бинарные массивы фиксированной разрядности для отображения в память (`mmap`), а также строит битовые маски рейтингов контента.

## 2. Построение Roaring-индекса (`step_build_bitmaps`)

### 2.1. Формат Roaring Bitmap
Для хранения множеств `dense_id` (uint32) используется библиотека `pyroaring`. Исходные `post_id` (int64) преобразуются в плотные индексы `dense_id` через биекцию массива `global_post_ids` (`mmaps/post_ids.bin`). Roaring Bitmap делит 32-битное пространство ключей на чанки по $2^{16} = 65\,536$ значений:
- При малом числе элементов чанк хранится как отсортированный массив `uint16` (Array Container).
- При плотном заполнении (> 4096 элементов) чанк конвертируется в битовую маску из 1024 64-битных слов (Bitmap Container, 8 КБ).
- При наличии длинных непрерывных последовательностей используется RLE-сжатие (Run Container).
Это обеспечивает минимальный расход оперативной памяти и сверхбыстрые побитовые операции пересечения (`AND`), объединения (`OR`) и вычитания (`AND NOT`) с использованием векторных инструкций процессора (AVX2/AVX-512).

### 2.2. Формат файлов `roarpack` и `index_*.bin`
Каждый шард `tag_shard=X` обрабатывается независимо через `ThreadPoolExecutor`. *Внимание: шаг `step_build_bitmaps` требует предварительного выполнения `step_build_mmaps` (возникнет `FileNotFoundError`, если `post_ids.bin` отсутствует).*
1. Извлекаются все пары `(tag_id, post_id)` шарда.
2. Группируются по `tag_id`, исходные идентификаторы постов (`raw_ids`, int64) сортируются по возрастанию.
3. Отсортированные `raw_ids` конвертируются в `dense_ids` (uint32) через биекцию `global_post_ids` с использованием `np.searchsorted`.
4. Битмап плотных индексов каждого тега сериализуется в байтовый блоб (`bm.serialize()`).
5. Все блобы конкатенируются в файл пакета: `shard_XXXX.roarpack`.
6. Смещения и размеры сохраняются в бинарный индекс: `index_XXXX.bin`.

#### Структура записи в `index_XXXX.bin`:
Каждая запись строго выровнена по 16 байт (формат `struct.pack('<iqi')`):
- `tag_id`: 4 байта (`int32`, Little-Endian)
- `offset`: 8 байт (`int64`, Little-Endian) — байтовое смещение в соответствующем `.roarpack`
- `length`: 4 байта (`int32`, Little-Endian) — длина сериализованного блоба в байтах

Сложность поиска тега в шарде: $O(\log N_{\mathrm{tags\_in\_shard}})$ через бинарный поиск по `index_XXXX.bin` либо $O(1)$ при загрузке индекса в хеш-таблицу памяти. Чтение самого битмапа требует ровно одного системного вызова `pread` без чтения окружающих данных.

## 3. Колоночные Memory-Mapped массивы (`step_build_mmaps`)

Традиционные реляционные СУБД создают высокие накладные расходы при сканировании миллионов записей для ранжирования и фильтрации. Модуль выгружает ключевые числовые поля в плоские C-массивы.

### 3.1. Сортировка и первичный ключ
Таблица постов строго сортируется по `id` (возрастание). Длина всех массивов строго равна общему количеству публикаций $N$. Порядковый номер строки $i \in [0, N-1]$ служит сквозным физическим индексом.

### 3.2. Состав файлов в `mmaps/`:
| Файл | C-Тип | NumPy Dtype | Назначение |
| :--- | :--- | :--- | :--- |
| `post_ids.bin` | `int64_t` | `np.int64` | Исходный глобальный ID поста на сайте |
| `epoch_day.bin` | `int32_t` | `np.int32` | Дата публикации в днях от эпохи Unix (Unix Day) |
| `w.bin` | `int32_t` | `np.int32` | Ширина изображения в пикселях |
| `h.bin` | `int32_t` | `np.int32` | Высота изображения в пикселях |
| `score.bin` | `int32_t` | `np.int32` | Результирующий рейтинг (лайки минус дизлайки) |
| `fav_count.bin` | `int32_t` | `np.int32` | Количество добавлений в избранное |
| `is_deleted.bin`| `uint8_t` | `np.uint8` | Флаг удаления (0 или 1) |
| `is_pending.bin`| `uint8_t` | `np.uint8` | Флаг нахождения на премодерации (0 или 1) |
| `rating.bin`    | `uint8_t` | `np.uint8` | Численный код рейтинга (`0: s`, `1: q`, `2: e`) |
| `file_ext.bin`  | `uint8_t` | `np.uint8` | Численный код расширения (`0: png`, `1: jpg/jpeg`, `2: webp`, `3: gif`, `4: webm`, `5: mp4`, `6: swf`, `7: other`) |

### 3.3. Системные Roaring-битмапы (`*.roar`)
Генерируются бинарные Roaring-битмапы для мгновенной фильтрации контента по цензурным категориям, статусу удаления и типам медиа:
- **Цензурные категории:**
  - `rating_s.roar`: Safe (безопасный контент)
  - `rating_q.roar`: Questionable (сомнительный / эротика)
  - `rating_e.roar`: Explicit (откровенный 18+)
- **Фильтрация медиа и статуса:**
  - `not_deleted.roar`: Активные неудаленные посты без заблокированных форматов (`(~is_deleted) & (file_ext < 6)`)
  - `media_image.roar`: Статичные растровые изображения (png, jpg, webp: `file_ext <= 2`)
  - `media_video.roar`: Анимации и видео (gif, webm, mp4: `3 <= file_ext <= 5`)

### 3.4. Архитектурные преимущества
- **Zero-Copy & Zero-Deserialization**: Процесс поискового демона монтирует `.bin` файлы через системный вызов `mmap(2)` за 1 миллисекунду.
- **Разделяемая память**: При запуске нескольких воркеров (например, веб-серверов) страницы памяти кэшируются ядром ОС (Page Cache) и не дублируются в RAM.
- **Векторизация (SIMD)**: Простые плоские массивы позволяют компиляторам и NumPy векторизовать предикаты вида `(fav_count > 50) & (score > 10) & (w >= 1920)`.
